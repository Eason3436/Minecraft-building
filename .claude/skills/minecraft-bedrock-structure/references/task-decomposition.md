# 任務拆解與任務書

大建築做壞的方式通常不是「不會蓋」，而是：一口氣寫一個 800 行的生成器，中途上下文用完、或發現屋頂與室內互相打架、或反覆回頭問使用者小事。這份文件定義三件事：**怎麼判斷拆不拆、拆了怎麼組、用一份任務書讓整個過程可續跑且不需中途發問**。

目錄：1 拆或不拆｜2 模組化規範｜3 任務書 build_plan.md 範本｜4 自主執行與停下來問的邊界｜5 續跑規則｜6 本專案實例

---

## 1. 拆或不拆：看耦合度，不是看大小

問一個問題：**模組之間是不是只靠「接口約定」就能各自成立？**

| 情況 | 判斷 | 做法 |
|---|---|---|
| 鐵路合集、車站群、村莊民宅×N、城牆段、橋段 | 模組之間只共用軌道高度／道路寬／牆面接縫這類**數字約定** | **拆**：每個模組獨立函式或獨立檔案、獨立結構 id；先定接口表，再各自建，最後組裝或交付多個 id |
| 民宅、教堂、太空梭、塔 | 室內配置、樓梯位置、屋頂形狀互相牽動；改屋頂就得改頂樓房間 | **不拆結構，但拆 pass**：同一個生成器內按「骨架 → 細節 → 室內 → 景觀照明」四個 pass 依序做，每個 pass 是獨立函式 |
| 刷怪塔、紅石機關、農場 | 機制正確性優先，外觀次之；一層對了其餘是複製 | **先做一個最小單元驗證**（一層、一個模組），確認尺寸、水流、漏斗路徑，再複製擴展，最後包外殼 |
| 超過 64×64 的單體 | 遊戲限制強迫分件，但設計上是一體 | 在**同一個陣列**上建完整模型，存檔時切成 64×64 分件（各自驗證），說明寫偏移；不要各分件分開設計 |

決定後把結論寫進任務書的「拆解決策」欄，之後不再猶豫。

模型能力也是因素：越弱的模型越該拆細（每個模組 100–200 行以內），越強的模型可以一氣呵成。不確定就拆——拆的代價只是多幾個函式，不拆的代價是整個重來。

## 2. 模組化規範

拆成模組時，遵守這幾條，最後組裝才不會對不上：

1. **每個模組是一個函式**，簽名固定：`def build_<name>(M, ox, oy, oz, **opts)`，內部所有座標加上偏移。`M` 是 `StructureBuilder`。
2. **接口表先寫**：在任務書列出每個模組的「外框尺寸、入口面向、接縫高度、與鄰接模組的對齊點」。例：`軌道面 Y=2、軌道中心 X=4、月台面 Y=3`。
3. **共用調色盤**：所有模組從同一份調色盤取方塊（任務書第 5 節），風格才一致。可以有模組專屬點綴色，但主材不變。
4. **共用元件函式**：燈柱、窗、樹、欄杆這種會重複的東西寫成小函式放在生成器最上面，模組呼叫它們。同一種燈柱在全區長一樣。
5. **組裝函式最後呼叫**：`build_all()` 依接口表把模組放到正確偏移；合集則對每個模組各自 `StructureBuilder` + `save`，同一個 namespace、不同 id。
6. **每完成一個模組就渲染一次**、更新任務書勾選，不要等全部做完才看。
7. 模組超過 200 行就再拆（例如「主殿」拆成「台基」「柱網」「屋頂」「室內」）。

## 3. 任務書 `work/<專案>/build_plan.md` 範本

首輪就寫好，之後只更新勾選與「變更記錄」。這份文件是你和未來的自己（新對話）之間的合約；寫得夠具體，才能中途接手不重來。

```markdown
# <建築名稱> 任務書

## 1. 需求摘要
- 使用者原話重點：…
- 建築類型／用途：…
- 風格關鍵字：…（例：日式町屋、深色木構、白牆、黑瓦）
- 參考圖：有/無；有的話觀察清單見第 8 節
- 交付：<建築名稱>.mcpack + 使用說明 + 整體渲染 + 內部剖視

## 2. 尺寸與座標
- 外框：寬 X=__ × 高 Y=__ × 深 Z=__（NBT size=[X,Y,Z]）
- 原點：最小角；地基高度 Y=__；正面朝 __（+Z/−Z/+X/−X）
- 目標版本：__；mojang-blocks.json 版本：__；block_version：__
- namespace:id：__:__（合集列全部 id）

- 耦合度判斷：拆成模組 / 單體分 pass / 最小單元先驗證 / 單體切分件
```

## 4. 自主執行與「停下來問」的邊界

任務書寫好之後，預設是**連續執行到交付**。中途發問會打斷使用者，而且大多數問題你自己就能決定。原則：

**自己決定，寫進任務書就好**：名稱與 id、風格內的材質選擇、房間配置、樹的位置、燈的種類、渲染角度、分件切法、任何「兩種都合理」的美學選擇。

**只有這些才停下來問**：
- 尺寸超過 64×64 且使用者沒說可否分件、也沒說可否縮小。
- 來源檔損毀或與描述矛盾（例如說是 mcstructure 但實際是 Java schematic）。
- 需求互相矛盾且會導致重做（例如「單一結構」又要「200 格長」）。
- 使用者明確要求先看規劃再開工。

問的時候一次問完所有問題，附上你的預設選項，讓使用者只需回「好」。

## 5. 續跑規則（上下文溢出或新開對話時）

建模很耗上下文，溢出是正常的，不要慌，也不要重頭來：

1. 先讀 `work/<專案>/build_plan.md`，看模組表哪些已勾選、變更記錄最後一條是什麼。
2. 列 `work/<專案>/` 現有檔案：生成器 `.py`、`.mcstructure`、預覽 `.png`。有 `.py` 就跑一次確認還能產出，不要重寫。
3. 從第一個未勾選的模組繼續；namespace、id、調色盤、尺寸一律沿用任務書，不重新命名。
4. 每完成一個模組更新勾選與變更記錄，讓下一次溢出也能接。
5. 交付前重跑完整生成器 + 渲染 + 打包，確保最終檔案來自同一份程式碼。

## 6. 本專案實例

| 建築 | 拆解方式 | 為什麼 |
|---|---|---|
| 綠蔭雙軌鐵路系統合集（10 個結構） | 拆成模組：直線／轉彎／車站各自 id，接口是軌道高度與寬度 | 模組間只靠數字約定，使用者要自由拼接 |
| 木石隧道與三風格車站 | 拆成 4 個模組共用 `base()`、`bench()`、`lamp()` 元件，同 namespace 多 id | 三個車站風格不同但月台接口一致 |
| 聖彼得大教堂（30–40 分件） | 單一大陣列建完整模型，存檔時切 64×64 分件，`/function` 一鍵放置 | 設計上是一體，遊戲限制才分件 |
| 夜幕六型主動刷怪塔 | 先做一層驗證水流、漏斗、距離，再複製六層，最後包外殼 | 機制優先，錯一層等於錯六層 |
| 亞特蘭提斯太空梭、晴空之塔 | 單體，按骨架→細節→室內→景觀分 pass | 外殼與室內互相牽動 |

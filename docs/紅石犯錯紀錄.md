# 紅石機器犯錯紀錄

來源：「紅石計數顯示器」（2026-09-24，v1 → v2）。以後做任何紅石機器前，先讀完這份紀錄，並逐條檢查。

## 一、使用者回報的錯誤

### 1. 七段顯示器左右顛倒（v1 全部數字都是鏡像）
- **錯誤**：顯示器面向北（-Z），玩家站在北邊面向南看。這時玩家的**左手是東（+X）**，我卻把「左側的段」（f、e）放在西邊（小 X），整個數字變成鏡像。
- **連帶錯誤**：渲染圖裡的 1～9 預覽條，是照「X 由小到大、從左往右」畫的，同樣是鏡像，所以預覽條也沒幫我抓到錯。說明檔裡「+1 在左／重置在右」也寫反過一次。
- **規則**：
  - 先寫下「玩家站在哪、面向哪、左手是哪個軸向」，再擺顯示元件。面向南 → 左手是 +X；面向北 → 左手是 -X；面向東 → 左手是 -Z；面向西 → 左手是 +Z。
  - 模擬器測試要輸出「玩家視角」的文字圖（例如用 `#` 和 `.` 畫出 1～9），親眼確認數字是正的，不能只比對段的名稱。
  - 預覽圖、說明檔裡的左右描述，都要依玩家視角產生，並且對照同一份文字圖。

### 2. 體積過大、線路太鬆（v1 是 40×42×12，v2 壓到 17×25×12）
- **錯誤**：
  - 每一段各做一個獨立模組、各拉一條類比刻度線，模組之間留很大的間距，再用長長的「漏斗式走線」收回顯示器。
  - 重置做了一整套比較器迴路閂鎖＋「R 滿 8 把」偵測＋常數紅石粉鏈。
  - 按鈕放在顯示器前方，卻用 60 格以上的長線拉到遠處的核心。
  - 另外加了一大片觀賞區地板和留邊。
- **v2 的壓縮手法**（以後直接採用）：
  - 串接式解碼：`(A∧¬B)` 的輸出可以直接併進下一個閘的後端。只要滿足「前項成立時後項的 ¬C 一定成立」，就能一欄串到底，每段只要 3 格寬。例如 `((U2∧¬U4)∨U5)∧¬U7 ∨ U8`。
  - 兩段共用一條刻度線：左右兩側各掛一段（西側刻度＋西閘欄、東側刻度＋東閘欄）。
  - 讓每段的出口欄剛好對準顯示器的輸入欄，就不用另外繞線。
  - 往上送數位訊號用「方塊＋火把」塔（兩支火把＝不反相），只佔 1 格寬。
  - 控制台和計數核心放在顯示器旁邊，不要拉長線。
  - 能用「保持條件＋延時」就別做完整閂鎖（但要把時序假設寫進說明）。
- **規則**：設計前先估算總體積，並列出最長的一條線。任何超過 10 格的走線，都要先想能不能改變擺位讓它消失。

## 二、我自己抓到的錯誤（模擬器或檢查發現）

### 3. 紅石粉斜向串線（犯了兩次）
- 「+1」線走在 Y1 的紅石粉，和旁邊高一格（Y2）升降梯的紅石粉斜向相鄰。因為上方是空氣，兩條線會自動連在一起，訊號就互相污染。v2 的延時線在 Y1，也和 Y2 的刻度線斜向相鄰。
- **規則**：任何兩條紅石粉只要高低差 1、水平相鄰，而且較低那格的正上方不是導電方塊，就會連線。每條不同高度的線都要檢查，必要時在較低紅石粉的正上方放一個導電方塊切斷。

### 4. 走線函式的中繼器方向錯
- 自己寫的 `route()`，在轉角附近用了「下一段的方向」當成中繼器的朝向，結果出口的中繼器全部朝錯方向。
- **規則**：中繼器朝向＝它所在這一段的前進方向。轉角格只能放紅石粉，不能放中繼器。

### 5. 基岩版方向狀態很容易搞反（開工前查 wiki 才發現）
- `unpowered_repeater` 和 `unpowered_comparator` 的 `minecraft:cardinal_direction` 是**從輸出端指向輸入端**，也就是和輸出方向**相反**。要往北輸出，就要填 `south`。
- 之前的「夜幕六型主動刷怪塔」是照「輸出方向」填的，**可能是錯的**，要回頭檢查。
- `torch_facing_direction` 的 wiki 說明有歧義，所以只用站立火把（`top`）。
- 按鈕的 `facing_direction`：2＝貼在方塊北面、朝北。
- 漏斗和投擲器的 `facing_direction` 都是輸出方向（0 下、1 上、2 北、3 南、4 西、5 東）。
- **規則**：每種有方向的紅石方塊，都先查 minecraft.wiki 基岩版的 block states（用 `?action=raw` 抓原始碼），不要照 Java 版的直覺或舊專案抄。

### 6. 其他小錯
- 用 bash heredoc 寫 Python 時，`\\n` 被展開成真的換行，告示牌字串就斷掉了。多行文字改用 `|` 分隔，輸出時再換成 `\n`。
- 渲染字型（微軟正黑體）沒有「≥」這個字，圖上會變成方框。圖上文字避免數學符號。
- 渲染圖的標題比面板還寬，互相重疊。每個面板的標題要短。
- `package_structure.py` 要求交付目錄是空的。更新版本時，先刪掉自己的舊交付檔，再用 `--previous-manifest` 加 `--version` 沿用原本的 UUID。

## 三、做紅石機器的檢查清單

1. 先寫任務書：機制原理、訊號強度表、每段邏輯公式、玩家視角（面向與左右）。
2. 開工前用 wiki 核對每個方塊的方向狀態，也要核對導電性：投擲器、紅石燈會導電；漏斗、玻璃、紅石方塊不導電。還要注意基岩版紅石粉不會自動指向機械元件。
3. 生成器要內建紅石模擬器（參考 `work/counter_display/machine.py`，注意 `work/` 不進 git）。至少要驗證：
   - 每個狀態的輸出（顯示器要畫玩家視角文字圖）
   - 不該受電的機械元件（投擲器、漏斗）確實不受電
   - 按鈕按下、放開的流程
   - 中繼器沒有被側鎖
4. 結構以模擬出的穩態存檔：紅石粉強度、中繼器／比較器亮暗、火把、燈、漏斗鎖定都要一致，比較器也要寫 `OutputSignal`。
5. 壓縮檢查：總體積、最長的走線、有沒有模組可以共用刻度線或串接。
6. 說明檔要寫清楚模擬的範圍和時序假設，並註明「尚未在遊戲內實測」。

## 附：有用的數據
- 投擲器／發射器（9 格）裝 n 把不可堆疊的物品，比較器讀到的訊號是：0, 2, 4, 5, 7, 8, 10, 11, 13（n=0..8），公式是 `floor(14·n/9)+1`。
- 紅石粉衰減刻度：第 i 格的值是 s−i。在第 i 格接一個中繼器，就能取出 s≥i+1。
- 強充能的方塊會供電給相鄰的紅石粉；弱充能的方塊（只被紅石粉供電）不會。
- 比較器可以隔著一個導電方塊讀取容器。

## 四、紅石二進位計算機（2026-09-25）的心得與差點犯的錯

### 7. XOR 在單一平面上一定要交叉（差點硬塞平面走線）
- 「兩個減法比較器 U−V、V−U 打進同一方塊」的 XOR，如果 U、V、輸出三者都要連到外面，拓撲上是 K3,3，平面不可能不交叉。
- **規則**：先判斷哪個輸入可以「在內部」（例如拉桿直接裝在樞紐方塊上，不需要從外面拉線），或把輸出改成就地點燈；
  真的要交叉就用上層紅石粉（Y+2，支撐在 Y+1），不要在平面上硬繞。

### 8. 上層紅石粉的支撐方塊會被弱充能
- 紅石粉會弱充能它腳下的方塊；弱充能方塊會點亮旁邊的紅石燈、餵旁邊中繼器的後端、比較器的後端。
- **規則**：上層走線的每個支撐方塊，都要確認四周同高度沒有燈、中繼器後端、比較器後端；燈不要直接放在會被走線經過的位置旁邊。
- 同樣地，上層紅石粉會和「高低差 1、水平相鄰」的紅石粉自動連線（第 3 條），兩條上層線要隔一格以上，必要時在低的那格正上方放阻隔方塊。

### 9. 「方塊樞紐」設計法（這次一次就模擬通過，建議沿用）
- 每個訊號存在一個被中繼器／比較器強充能的實心方塊上。
- 比較器後端直接讀樞紐方塊；側面一律由「背對樞紐的中繼器」餵入，確保是 15 或 0，減法不會出現殘值。
- OR ＝兩個比較器打進同一個方塊。分支＝樞紐四周接多個背對它的中繼器。
- 樞紐之間相鄰不會互傳（方塊不傳方塊），但樞紐旁邊不能放不相干的紅石粉（強充能方塊會供電給相鄰紅石粉）。

### 10. 顯示又左右顛倒（紅石二進位計算機 v1 → v2，使用者回報）
- **錯誤**：v1 是照「玩家站北側面向南」擺高低位（高位在東），邏輯上沒錯；但燈排放在電路板**最南端**，
  使用者自然會走到燈旁邊、從南邊看 → 看到的順序整個反過來。我只「規定」了觀看位置，卻沒有用配置「強制」它。
- **規則**：
  - 輸入和輸出要放在**同一個操作位置**（控制桌＋顯示牆），並用牆、桌子擋住其他方向，讓玩家只可能從一邊看。
  - 燈和拉桿要放在最靠近那個操作位置的一端；不要把顯示放在電路另一頭。
  - 模擬器測試要依「操作位置」輸出左右順序的文字圖（例：`NEG:. C64:# 32:. … 1:.`），拉桿順序也要一起印出來核對。
  - 需要換方向時，整台做 X 鏡像（中繼器／比較器 E↔W）最省事，再重跑全部測試。
